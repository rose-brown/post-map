# 지하철 소요시간에 대기시간 넣기

- 날짜: 2026-09-30
- 근거: 사용자 질문 "선릉 30분 이내 왜 이렇게 많아?" → 거리 계산은 맞았다(가장 먼 단지 직선 13.9km, 실효 시속 24~31km) — 많아 보이는 원인은
  **열차 대기시간이 빠진 것**(지하철 스펙 `2026-09-29-transit-layers-design.md` 4절). 사용자 결정: GTFS 배차간격으로 추정(B), **평일 07~09시**(A), 계획까지 추천으로.
- 이 문서는 지하철 스펙 4절(계산 규칙)을 고친다. 레이어·속성 이름(5절)은 그대로다.

## 1. 목표 (완료 기준)

1. `minSeolleung`·`minYeouido`·`minCityHall` = 도보 + **첫 탑승 대기** + 승차 + (환승 걷기 + **환승 대기**)… 의 최소.
2. 대기 = 그 역에서 그 방향 열차의 **07:00~09:00 평균 배차간격의 절반**.
3. 같은 열차로 계속 가는 동안(급행·직결 포함)은 대기가 없다.
4. `transit/run.ts --dry-run` 리포트에 **바꾸기 전(서버에 있는 값)과 후의 레이어별 단지 수**가 같이 나온다.
5. 실데이터 반영 뒤 교통 레이어 7개·원본 단지 속성·필터 버튼 결과가 새 값으로 바뀐다.

## 2. 확정된 결정

| # | 결정 | 이유 |
|---|---|---|
| W1 | 대기 = 배차간격 ÷ 2 (역에 아무 때나 도착한다는 가정의 기대 대기) | 시간표 맞춰 가는 사람(0)과 방금 놓친 사람(배차간격 전부)의 중간. 쓰는 사람이 받아들이기 쉬운 평균 |
| W2 | 시간대 **07:00:00 ≤ 도착 < 09:00:00** (평일, KTDB 서비스 `B1` 하나) | 사용자 결정 A. 기준역이 업무지구 — 출근 기준 |
| W3 | 배차간격은 **방향별**: 역 a 에서 다음 정차가 b 인 운행 수 n(a→b) 로 `7200 ÷ n`. 급행(a 다음 정차가 c)은 따로 센다 | 양방향을 합쳐 세면 대기가 절반으로 준다. 급행만 서는 구간은 급행 배차로 기다려야 맞다 |
| W4 | 07~09시에 그 방향 운행이 0 이면 하루 전체(05:00~24:00, 68,400초)로 `68400 ÷ n_하루 ÷ 2`. 하루에도 0 이면 그 탑승은 없다 | 첫차·막차만 다니는 구간이 경로에서 사라지지 않게. 실제로 거의 없을 것 — 몇 개인지 리포트에 낸다 |
| W10 | (구현 중 추가) 창 안에 그 방향만 0 이고 반대 방향(b→a)은 있으면 **반대 방향 창 안 배차**를 쓴다. 둘 다 0 이면 W4 | KTDB 2025-03 은 7호선 남행(`07-1D`) 이 16시 이후 75회뿐이다(북행 `07-1U` 204회) — 원본 결함. W4 만이면 노원·상봉 쪽 남행 출근 대기가 8분(실제 2~3분)으로 부풀었다. 드문 급행 패턴이 반대 방향 배차를 얻는 부작용은 기준역에서 먼 구간뿐이라 받아들인다 |
| W5 | 그래프를 **정류장(P)** 과 **열차 위(R: a→b 구간을 달리는 중)** 로 나눈다. 탑승 `P(a)→R(a→b)` = 대기(a→b)+승차(a→b), 계속 `R(a→b)→R(b→c)` = 승차(b→c)(실제 운행에 a,b,c 가 이어서 있을 때만), 하차 `R(a→b)→P(b)` = 0, 환승 `P(a)→P(b)` = `transfers.txt` 초 | 대기를 "탈 때마다" 넣으려면 지금 타고 있는지를 알아야 한다. 지금 그래프(정점 = 역)는 그걸 모른다 |
| W6 | 승차 시간은 지금처럼 **도착시각 차의 중앙값**(구간 a→b 별) | 바꾸지 않는다 — 이번 변경의 효과만 보이게 |
| W7 | 도보·2km·반올림·역세권 500m 규칙은 그대로 | 지하철 스펙 4절 |
| W8 | 같은 이름 다른 호선(`시청(1호선)`↔`시청(2호선)`)으로 갈아타는 것은 지금처럼 `transfers.txt` 간선 — 이제 그 뒤 탑승에 대기가 붙는다 | 환승 대기가 이 변경의 절반 |
| W9 | 직결 구간(두 호선이 같은 stop_id)에서 **다른 운행으로 갈아타면** 하차 → 탑승이라 대기가 붙는다. 같은 운행이면 계속 간선이라 없다 | W5 에서 자연스럽게 나온다 |

## 3. 구조 (`scripts/transit/build.ts`)

- 새 순수 함수
  - `boardWaits(trips, window = [25200, 32400]): { waits: Map<'a>b', 초>, fallback: string[] }` — W2~W4. `fallback` = 하루 폴백을 쓴 키 (리포트용).
  - `buildWaitGraph(trips, transfers, waits): ReverseGraph` — W5·W6. 정점 키 `P:<stopId>`, `R:<a>><b>`.
  - `stationSecondsTo(g, targetStopIds): Map<stopId, 초>` — `secondsTo(g, targets.map(P:…))` 결과에서 `P:` 만 골라 키를 stop id 로 되돌린다. `minutesVia`·`transitProps` 는 그대로 쓴다.
- `buildReverseGraph` 는 **지운다** (run.ts 가 새 함수로 바뀌면 쓰는 곳이 없다). 그 테스트는 새 함수 테스트로 바꾼다.
- `secondsTo`(다익스트라) 는 그대로 — 정점 수가 역 ~800 → P ~800 + R ~1,700 으로 늘지만 배열 우선순위로 충분하다(기준역 3곳 × 수초 이내가 목표, 리포트에 시간 기록).

## 4. 실행·리포트 (`scripts/transit/run.ts`)

- dry-run 리포트에 추가: `before`(서버 원본 단지의 현재 `minSeolleung` 등으로 센 레이어별 수), `after`(새 값), `waits`(07~09시 대기 분포: 중앙·최대, 폴백 W4 개수), `sanity` 에 강남→선릉·시청(2)→여의도 외 **대기 포함 값**.
- 쓰기 경로·레이어·사본 규칙은 바꾸지 않는다 (지하철 스펙 D6·D7·D8). 실행 뒤 `node scripts/presets/run.ts` 는 필요 없다(스키마 변화 없음) — 하지만 lead50 규칙대로 결과 확인용 dry-run 은 한다.

## 5. 테스트 (`tests/transit.test.ts`)

- `boardWaits`: 방향별로 센다(반대 방향 운행은 안 센다), 07~09시 밖 운행은 안 센다, 급행(다음 정차가 다름)은 다른 키, 창 안 0 이면 하루 폴백, 하루도 0 인 키는 없다.
- `buildWaitGraph` + `stationSecondsTo`:
  - 한 번에 가는 경로 = 대기 1회 + 승차 합 (중간역에서 대기 없음).
  - 환승 경로 = 대기 + 승차 + 환승 + **대기** + 승차.
  - 대기가 큰 직행보다 대기가 작은 환승이 빠르면 환승을 고른다.
  - 운행에 a,b,c 가 이어서 없으면 `R(a→b)→R(b→c)` 가 없다 (급행 a→c 운행과 완행 a→b→c 를 섞지 않는다).
  - 기준역 자신 = 0, 역방향 운행만 있으면 닿지 않는다.
- 기존 `minutesVia`·`transitProps`·`copyRow` 등 테스트는 그대로 통과.
- 실데이터: 대기 포함 강남→선릉이 4분 + 1~2분 안팎, 판교→선릉·김포공항→여의도가 대기만큼 늘었는지. 레이어별 before/after 수를 로그에 남긴다.
