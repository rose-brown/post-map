## 1. 확정된 결정 (스펙 D1~D11 요약)

- **온라인 우선** — 서버가 진실의 원천, IndexedDB 는 읽기 경로에서 빠지고 이관 원본으로만 남는다.
  대가: **신호가 없으면 새 입력이 막힌다.** PRD 2.1·2.2 의 현장 사용과 상충하는 것을 알고 고른 선택.
- **로그인 없음.** 접근 제어는 프로젝트 uuid 를 `?p=` URL 과 `x-project-id` 헤더로 보내는 **비밀 링크**.
  링크를 아는 사람이 곧 권한이다 — 읽고 쓰고 **지운다**. 사람 단위 역할은 없다.
- **PostGIS 를 쓰지 않는다.** `geometry` 는 jsonb. 공간 연산이 전부 클라이언트 turf 라 서버가
  공간 질의를 하지 않는다. 필요해지면 컬럼 타입 변경으로 전환한다 (PRD 4.4 와 어긋나는 유일한 지점).
- 이미지는 **바이트만 Storage**(public 버킷 `blobs`, 경로 `<projectUuid>/<blobId>`),
  **관계와 경로는 `public.blobs` 테이블**(RLS 보호).
- `repo.ts` 의 공개 함수 14개 **시그니처를 유지**했다. 스토어·UI·지도는 거의 손대지 않았다.

## 2. 구현 중 찾은 것 — 기존 코드의 버그 세 개

계획에 없던 것들이고, 전부 데이터가 조용히 사라지는 경로였다.

1. **`flush()` 가 트랜잭션 전에 큐를 비웠다.** 실패하면 `console.error` 만 찍어서 실패한 쓰기가
   그대로 사라졌다. 이제 성공한 테이블만 비우고, `saveState 'error'` + `lastSaveError()` 로 알린다.
2. **`init()` 이 프로젝트를 못 찾으면 `ready:true` 로 빈 지도를 띄웠다.** 데이터가 지워진 것으로
   오인되는 경로다. 지금은 던지고 `StartGate` 가 오류·재시도를 보여준다.
3. **저장 상태 표시가 `hidden lg:inline` 이었다.** 모바일에서 저장 실패가 아예 안 보였다.
   PRD 2.1 의 주 사용자가 모바일이므로 실패 상태만 화면 크기와 무관하게 띄운다.

## 3. 계획 문서의 오류 두 개 (계획을 읽을 때 주의)

`docs/superpowers/plans/2026-09-27-phase3-multidevice-sync.md` 에 이렇게 적혀 있지만 틀렸다.

- **`unwrap()` 은 존재하지 않는다.** `Persistable<T>` 는 `T` 에 브랜드를 더한 타입이라 구조적으로
  이미 `T` 다 — 꺼낼 필요가 없다. 만들면 저장 게이트를 우회하는 경로가 된다.
- **`SaveState` 는 객체가 아니라 문자열 유니온** `'idle'|'pending'|'saved'|'error'` 이고 이미
  `'error'` 가 있었다. 시그니처를 유지하고 메시지만 `lastSaveError()` 로 따로 뺐다.

## 5. 지금 막혀 있는 지점 — 여기서 시작하라

`supabase/schema.sql` 을 대시보드 SQL Editor 에서 실행했고 **테이블은 생겼다.** 그런데 RLS 확인이 갈렸다.

```
(1) 헤더 없이 projects 조회  → []        기대대로 (목록 열람 차단)
(2) 헤더 없이 projects INSERT → 42501    ✗ "create new project" 정책이 안 먹는다
```

`(1)` 의 `[]` 는 판별 근거가 못 된다 — **정책이 하나도 없어도** RLS 는 전부 거부하므로 같은 결과가 나온다.

**가설 1: 정책이 안 만들어졌다.** `schema.sql` 을 두 번 이상 실행했다면 두 번째는
`create table … already exists` 에서 멈추고, Supabase SQL Editor 는 한 트랜잭션이라 뒤의
`create policy` 가 전부 날아간다. 테이블만 있고 정책은 없는 상태가 이렇게 만들어진다.
(1)·(2) 의 증상이 정확히 이 그림과 맞는다.

**가설 2: `sb_publishable_…` 키가 `anon` role 로 매핑되지 않는다.** 정책이 전부 `to anon` 이라
role 이 다르면 적용되지 않아 같은 증상이 난다.

### 판별 방법

대시보드 SQL Editor 에서 실행한다 (Editor 는 마지막 결과만 보여주므로 하나씩).

```sql
select schemaname, tablename, policyname, cmd, roles::text, permissive
from pg_policies where schemaname in ('public','storage')
order by schemaname, tablename, policyname;
```

- 행이 **6개**(projects 2개 + layers·features·blobs 각 1개 + storage 2개) 보이면 → 가설 1 탈락, 가설 2 조사
- 비어 있거나 적으면 → 가설 1 확정. `schema.sql` 의 `create policy` 부분만 다시 실행한다
  (`drop policy if exists` 를 앞에 붙여야 재실행이 안전하다)

확인 스크립트는 세션 스크래치패드에 있었고 휘발된다. 다시 만들려면 계획 문서 Task 1 Step 4 를 보라.

## 9. 이어진 세션 — RLS 막힘 해소와 Phase 3 확인 마무리

Supabase MCP 가 붙어 대시보드 없이 SQL 을 직접 돌렸다.

### 원인: 정책은 다 있었다. RETURNING 이 막았다

`pg_policies` 에 정책 7개가 모두 `{anon}` 으로 있었다. HANDOFF 의 두 가설(정책 누락·신형 키 role)은 둘 다 아니었다.
anon + 헤더 `{}` 로 롤백 트랜잭션에서 재현하니 `insert` 는 통과, `insert … returning id` 만 42501.
RETURNING 으로 돌려줄 행은 SELECT 정책(`id = 헤더`)도 통과해야 하는데 헤더가 없어 NULL 이다.
앱의 `createProject`(`.insert().select('id')`)도 같은 경로라 **새 프로젝트를 만들 수 없는 상태였다.**

수정: uuid 를 클라이언트가 `crypto.randomUUID()` 로 만들어 헤더에 먼저 박고 INSERT.
예외 정책 `"create new project"` 와 `makeAnonClient()` 를 삭제했다 (원격 DB 에도 적용).

### 두 번째 발견: 이미지 삭제가 403 이었다

Storage 목록 열람 판정 중, 올린 탐침 객체가 **지워지지 않았다**(403). Storage API 는 삭제 대상을 SELECT 로 찾는데
목록 차단을 위해 SELECT 정책을 일부러 비워 뒀기 때문이다. `deleteBlob`·`purgeBlobsOfFeatures` 가 throw 하므로
이미지 달린 피처·레이어 삭제가 실패했을 것이다.

수정: `storage.foldername(name)[1] = x-project-id 헤더` 인 SELECT 정책. Storage API 도 헤더를 넘긴다는 것이 실측됐으므로
스펙 3절에 적힌 대로 업로드·삭제 정책도 같은 조건으로 조였다.
