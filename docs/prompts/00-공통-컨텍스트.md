아래 블록을 각 Phase 프롬프트 맨 앞에 그대로 복사해서 넣으세요.

## 프로젝트 개요

**범용 지도 편집 플랫폼**을 만든다. 특정 도메인(부동산 임장, 상권 분석, 시설물 관리)에 하드코딩하지 않고,
사용자가 **레이어와 속성 스키마를 직접 정의**해서 여러 용도로 쓸 수 있는 도구다.
도메인별 차이는 "템플릿"으로 흡수한다.

핵심 사용 흐름:

1. 지도 위에 point / line / polygon 을 직접 그린다
2. 그린 도형마다 **정보 페이지**가 붙는다 — 정해진 속성 필드 + 자유 블록(메모·사진·체크리스트·파일)
3. 도형에 공간 연산을 건다 — 동심원(다중 반경 링), 거리 버퍼, 꼭짓점 편집, 합집합·교차·차집합
4. 주소를 검색해 지점을 찍고, 두 지점 간 소요시간·경로를 본다
5. 외부 데이터를 레이어로 얹는다 — 파일 업로드(GeoJSON/SHP/KML/CSV), 공공데이터 API, 배경 타일/WMS
6. PC와 모바일 브라우저에서 같은 기능을 쓴다 (반응형 웹, 네이티브 앱 없음)

## 기술 선택과 근거 (바꾸려면 여기를 먼저 읽을 것)

**왜 Kakao/Naver 지도 SDK가 아니라 MapLibre인가**
이 제품의 핵심은 벡터 작도와 공간연산이다. Kakao·Naver의 JS SDK는 자사 지도 표시를 전제로 한
오버레이 API만 제공해서, 수만 개 피처 렌더링·벡터타일·GeoJSON 스타일 표현식·꼭짓점 편집을 전부
직접 만들어야 한다. MapLibre는 이 기능들이 기본 제공이고 Terra Draw·deck.gl 생태계가 붙는다.

**그 대신 잃는 것**
Kakao/Naver 지도의 국내 POI·건물 라벨 품질, 그리고 SDK에 딸려오는 길찾기 연동. 배경지도는 VWorld로 대체한다.
(각 사 지도 SDK의 타일을 MapLibre에 직접 끼워 쓰는 것은 이용약관상 허용되지 않는 것으로 보고 설계한다.)

**외부 API 결과의 저장 가능 여부 — 이 제품에서 가장 중요한 제약**

이 제품은 사용자가 찍은 지점과 그 주소를 **영구 저장**하는 것이 본체다. 그런데 상용 지도 API 중에는
응답 데이터의 저장을 금지하는 곳이 있다.

카카오 로컬 API의 경우, 카카오 데브톡의 공식 답변 기준으로:
- 검색 결과를 **타사 지도 SDK 위에 표시하는 것 자체는 허용**된다 ("타사 지도SDK와 혼용하여 사용하셔도 약관 상 이슈는 없습니다")
- 그러나 **"로컬API 결과값은 어떠한 형태로든 저장하여 사용할 수 없고 실시간 호출로만 이용할 수 있습니다"** — 장소명·좌표를 기기나 서버에 저장하는 것, 그리고 응답을 가공한 데이터를 저장하는 것도 불허

따라서:

1. **저장이 필요한 지오코딩·주소검색은 공공데이터포털 경유로 발급한 국토교통부 지오코더 API / 검색 API를 쓴다.**
   두 API 모두 포털 상세 페이지에 **"이용허락범위 제한 없음"**이 명시되어 있어, 응답을 저장·가공해도 되는지가
   문서로 확인된다. 지오코더는 일 40,000건 제한. (대안: juso.go.kr 도로명주소 API)
2. 카카오/네이버 API를 쓸 경우 **실시간 조회·일시 표시 용도로만** 쓰고, 그 결과를 IndexedDB나 DB에 넣지 않는다.
3. **경로·소요시간도 같은 문제를 받는다.** 소요시간을 피처 속성으로 저장하려면 그 제공자의 약관이 저장을 허용해야 한다. Phase 2에서 제공자를 고를 때 요금·기능보다 이 항목을 먼저 확인해라.

**이 조사의 한계를 알고 있어라.**
- 카카오 정책의 근거는 공식 약관 문서가 아니라 카카오 데브톡 담당자 답변 2건이다.
- vworld.kr 사이트는 크롤링이 막혀 있어 **VWorld 자체 오픈API 이용약관과 검색 API 2.0 파라미터 스펙을
  직접 읽지 못했다.** vworld.kr 직접 발급 경로를 쓸 거라면 약관을 먼저 읽어라.
- 조사 시점은 2026년 9월이고 정책은 바뀐다. **서비스 공개 전에 각 제공자에게 직접 확인해라.**

**어댑터 경계를 반드시 둘 것**
`GeocodingProvider`, `RoutingProvider`, `BasemapProvider` 인터페이스를 두고 구현체를 갈아끼울 수 있게 한다.
공개 서비스 → 폐쇄망 전환, 또는 Kakao → Naver 교체가 코드 전면 수정 없이 되어야 한다.
**단, Phase 1에서는 인터페이스만 정의하고 구현체는 하나씩만 만든다. 과설계 금지.**

## 불변 규칙

1. **저장 좌표계는 EPSG:4326 (WGS84 경위도) 단일**. 업로드·표시 단계에서만 변환한다. 원본 좌표계는 메타데이터로 보존.
2. **거리·면적은 측지 계산**. 화면 픽셀이나 단순 위경도 차이로 계산하지 않는다. 동심원 반경 1km는 지도상 어디서든 실제 1km여야 한다.
3. **API 키는 클라이언트 번들에 넣지 않는다.** Phase 1·2는 Vite 개발 프록시, Phase 3부터는 Supabase Edge Function 프록시를 쓴다. 도메인 제한 방식 키(VWorld 등)만 예외로 하되 주석으로 명시한다.
4. **모든 지오메트리는 GeoJSON으로 주고받는다.** 내부 표현을 따로 만들지 않는다.
5. **모바일 우선 레이아웃.** 지도 영역이 줄어드는 게 아니라 패널이 바텀시트로 바뀐다.
6. **좌표·속성 스키마는 사용자가 정의한다.** 도메인 용어(매물, 단지, 임장)를 코드에 박지 않는다. 템플릿 데이터로만 넣는다.
7. **저장 금지 API의 응답은 저장하지 않는다.** 외부 API를 붙일 때마다 그 제공자가 응답 저장을 허용하는지 확인하고, 허용하지 않으면 그 결과는 화면 표시용으로만 쓴다. 각 Provider 구현체에 `canPersistResults: boolean` 를 두고, `false` 인 제공자의 결과가 저장 경로로 흘러가지 않게 타입 수준에서 막아라.

## 데이터 모델 (전 Phase 공통)

```
Project        지도 하나. 이름, 설명, 초기 뷰포트, 소유자
 └ Layer       레이어. 종류(vector | file | tile | api), 표시여부, 순서, 스타일, 속성 스키마
    └ Feature  도형 하나. GeoJSON geometry + properties + 정보 페이지
       ├ properties  스키마에 정의된 필드값 (타입 있음)
       └ blocks      자유 블록 배열 (text | heading | todo | gallery | files | callout | divider)

PropertySchema  레이어에 붙는 필드 정의: { key, label, type, unit?, required?, options? }
                type: text | number | date | select | multiselect | boolean | url | phone
Template        스키마 + 블록 프리셋 묶음. 예: "임장 기본", "설비 점검", "상권 조사"
```

`Feature.properties`는 **스키마에 정의된 필드** + **스키마 밖 자유 필드**를 모두 허용한다(하이브리드).
스키마 필드는 테이블 조회·필터·집계 대상이고, 자유 필드와 블록은 조회 대상이 아니다.

## 작업 규칙 (Claude Code에게)

- 요청한 범위만 구현한다. 요청하지 않은 기능을 "있으면 좋을 것 같아서" 추가하지 않는다.
- 요청이 잘못됐다고 판단되면 **한 문장으로 말하고, 요청한 대로 계속 진행**한다. 임의로 범위를 좁히거나 넓히지 않는다.
- 스텁·`TODO`·플레이스홀더를 남기지 않는다. 각 Phase의 완료 기준을 전부 충족시킨다.
- 외부 API 응답 형식은 추측하지 말고 공식 문서를 확인한다. 확인 불가하면 그 지점을 코드 주석과 최종 보고에 명시한다.
- 문서(README, 주석)는 필요한 만큼만 쓴다. 요약 섹션이나 보일러플레이트로 분량을 채우지 않는다.
- 커밋은 기능 단위로 쪼갠다.
